# Architecture E2E — hub

<!-- The hub's instructions for every coding agent. Claude Code loads this through CLAUDE.md

This folder is a hub, not an app. It holds the project's git repos under `repos/` plus
the shared context, the local dev stack and the software factory for requirements that
span several of them. The hub is its own git repo (its GitHub issues are the factory's
queue); the repos under `repos/` are gitignored here and each keeps its own remote,
branches and PRs. Never commit hub files into a repo, or repo files into the hub.

## Project documents — the source of truth

`docs/` holds the project's BRD (`docs/brd.md`), specs (`docs/specs/`), ADRs
(`docs/adr/`) and snapshots of every external source they came from (`docs/sources/`).
Read the parts a task touches before anything else. They outrank, in order: the code
in `repos/`, the issue being built, and external sources (always through their
snapshots). When an issue repeats them, rely on the documents; when it contradicts
them, flag it for a human. Conventions and IDs: `docs/README.md`. Tools:
`factory/bin/docs check | list | cites <id>`, `/docs-sync` when a source may have changed.
Mode and purpose of this hub: `factory/hub.json` (`/hub-init` sets them).

## How the pieces connect

Three repos, one product (see [ADR-0001]). Specs in reading order: `docs/specs/README.md`.

```
 browser ── arch-web (React SPA, nginx) ──REST /api/v1 + OIDC token──▶ arch-api (Go, gin+Huma)
    │                                                                    │   │
    └──── OIDC Auth Code + PKCE ──▶ Keycloak realm `arch` ◀── JWKS ──────┘   │ pgx/sqlc
 team CI ── arch CLI (from arch-api/cmd/arch) ── client credentials ─▶ Keycloak │
    └────────── POST /api/v1/import (YAML) ─────────────────────▶ arch-api     ▼
                                                                    PostgreSQL 16 (RDS in prod)
 arch-deploy: Helm chart (api, web, migrate job), Keycloak realm export → EKS; images from GHCR
 traces: arch-api ──OTLP──▶ collector (Jaeger locally)
```

- **Contract:** `arch-api/api/openapi.yaml` (OpenAPI 3.1, generated from Huma types) is the
  API contract [ADR-0003]; `arch-web` generates `src/api/schema.d.ts` from it [ADR-0007].
- **YAML format:** JSON Schema in `arch-api/schema/`, served at `/schema/arch.json` [ADR-0006].
- **Schema:** owned by `arch-api` only (goose migrations in `migrations/`) [ADR-0004].
- **Identity:** Keycloak; roles viewer/editor/admin, `teams` claim [ADR-0008].
- **Deploy:** `arch-deploy` installs images built by the app repos [ADR-0009].

## Cross-repo rules

- **Contract first.** When a change touches a service and its callers, write the
  interface (endpoint, request/response shape, error codes, events) before coding either side.
- **Backward compatible.** A service accepts old and new callers until every caller is
  merged and deployed. Never rename or remove a field in one step.
- **Merge order** is `merge_order` in `factory/repos.json`.
- **Branches** follow `factory/repos.json` → `branching` and the Branch strategy ADR:
  feature branches always start from the repo's base (normally `main`); PRs go to the
  base (`trunk`), to each env branch in turn (`env`), or to the current release
  candidate (`release`). Never merge an env or release branch into a feature branch.
- **Same branch name in every repo** for one requirement; link the PRs to each other
  and to the hub issue.
- **Secrets:** never read or print `.env*` files other than the examples.
- **API changes start in `arch-api`.** Change the Huma types, regenerate
  `api/openapi.yaml` (`make openapi`), merge, then regenerate `arch-web/src/api/schema.d.ts`
  (`pnpm gen:api`) in the same job. Never hand-edit either generated file, nor sqlc output.
- **Schema changes** are new goose migrations in `arch-api/migrations/`; existing ones are
  never edited (protected). Expand-then-contract for renames and drops.
- **Image or config changes** in `arch-api`/`arch-web` (new env var, port, probe) need the
  matching change in `arch-deploy` (values, `.env.example`, compose) in the same job.
- **Branching:** `trunk`, rebase onto `main` [ADR-0002]; every PR is merged by a human.

## Checks per repo

The gate runs `factory/checks/<key>.sh` from the hub inside each repo's worktree, with
`FACTORY_HUB`, `FACTORY_REPO_KEY` and `FACTORY_BASE` set. Run one by hand from a repo:
`FACTORY_HUB=<hub> FACTORY_REPO_KEY=<key> FACTORY_BASE=<base> bash <hub>/factory/checks/<key>.sh`.
Checks are lint, typecheck, unit tests and build only: no services, no watch mode.
While a repo is still empty (no `go.mod`, `package.json` or `charts/*/Chart.yaml`) its check
prints "nothing to check" and passes; once code lands the full checks run. They expect
`go tool golangci-lint` and `make openapi-check` in `arch-api`, and the pnpm scripts `lint`,
`typecheck`, `test` (run mode) and `build` in `arch-web`. Run `factory/bin/add-repo --redetect
<key>` after a repo's first code merges so its stack shows up in the table above.
`factory/bin/setup --checks` runs them all on each repo's base branch.

## Local services

`dev/bin/stack up [profile ...]` (podman, docker fallback), `down`, `reset` (drops data),
`ps`, `logs <svc>`. `dev/bin/apply-env [key ...]` copies `dev/env/<key>.env` to the repo's `.env`
(`--to <worktree> <key>` for a factory worktree). Built from [ADR-0004], [ADR-0008], [ADR-0009], [ADR-0013].

| service | profile | host ports | dummy credentials |
|---|---|---|---|
| postgres 16.14 | — | 5432 | `arch`/`arch` (owner, migrations), `arch_app`/`arch_app` (runtime, [ADR-0014]); databases `arch`, `keycloak` |
| keycloak 26.8.0 | — | 8180 (admin console at /admin) | admin `admin`/`admin` |
| jaeger 2.22.0 | `tracing` | 16686 UI, 4317 gRPC, 4318 HTTP | — |
| arch-api (golang 1.27) | `arch-api` | 8080 API, 9090 metrics | — |
| arch-web (node 26, Vite) | `arch-web` | 5173 | — |

- **Realm `arch`** (`dev/keycloak/arch-realm.json`, hub-owned until `arch-deploy` ships one;
  `ARCH_REALM_FILE=<path>` overrides): users `viewer`, `editor` (team `platform`), `admin`, all
  password `password`; clients `arch-web` (public, PKCE, `http://localhost:5173/*`), `arch-api`
  (audience), `arch-cli` (device flow), `arch-ci-platform` (secret `dev-ci-secret`, teams
  `[platform]`). Issuer is always `http://localhost:8180/realms/arch`; containers fetch keys from
  `http://keycloak:8080/...` (`OIDC_JWKS_URL`).
- **Run an app natively** (usual): `dev/bin/stack up`, `dev/bin/apply-env <key>`, then the repo's
  dev command (`go run ./cmd/arch-api serve`, `pnpm dev`). **As a container** (to work on a caller):
  `dev/bin/stack up arch-api`. A worktree instead of `repos/`: `ARCH_API_DIR=<path>` /
  `ARCH_WEB_DIR=<path>`. Entry scripts: `dev/arch-api/start.sh` (migrate + serve),
  `dev/arch-web/start.sh` (pnpm install + Vite).
- **Tracing:** `dev/bin/stack up tracing`, set `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317`.
- **New repos:** the first commit in `arch-api` and `arch-web` must add a `.gitignore` covering
  `.env` before anything else; `apply-env` has already put a dummy `.env` there.

## Factory notes

Read by every factory agent (intake, spec writer, builder, reviewers, approver) and by
/grill-issue. Keep each list short and specific to this project.

- **Domain:** Architecture E2E — an internal, self-hosted tool where engineers and architects
  model applications, infrastructure (EKS, RDS, ...), network paths (VPC, landing zone, Direct
  Connect) and on-prem systems as one typed graph, see an application's dependencies, and
  analyse a CR's impact across the whole chain. See `docs/brd.md` ([G-01], [BR-030]).
- **Language:** English for issues, specs, code, commits and UI copy ([NFR-007]).
- **High risk:** auth and permissions (token validation, role/team checks,
  `docs/specs/001_identity-access.md`); the change_log and audit ([NFR-003]); DB migrations;
  YAML import with `--prune` (deletes data, [SPEC-yaml-as-code-05]); impact traversal
  ([SPEC-impact-analysis-01] — wrong results mislead CR decisions); secret detection ([NFR-002]).
- **Sensitive data:** access/refresh tokens, `Authorization` headers, client secrets,
  `DATABASE_URL`, and every model attribute value (hostnames, IPs, ports, network paths,
  [NFR-001]). Never logged, never in error messages, never returned without auth.
- **Always escalate:** changes to auth middleware or role mapping; to `change_log` grants or
  writes; migrations that drop or rename; anything in `arch-deploy`; any new unauthenticated
  endpoint; changes to the secret-detection patterns.
- **Conventions:** Conventional Commits (`feat:`, `fix:`, ...). Go: `golangci-lint` clean,
  table-driven tests with `testing` (testify allowed), thin handlers with logic in services,
  RFC 9457 errors. Web: function components, TanStack Query for server state, Testing Library
  queries by role/label, Tailwind classes only. Generated files (`api/openapi.yaml`, sqlc
  output, `src/api/schema.d.ts`) are regenerated, never hand-edited.
- **Grill checklist:** which roles/teams may do it ([SPEC-identity-access-05]); does it write the
  change_log; does it change `openapi.yaml` (→ web regen); does it change the YAML schema, and
  stay compatible with existing team files; which environments; empty/loading/error states;
  still within [NFR-005] at 2,000 nodes / 10,000 edges; could it store or log a secret;
  does a canvas feature have a list alternative ([NFR-006]).

## Designing a requirement (/grill-issue)

Run `/grill-issue <idea, ticket or notes>` in Claude Code from the hub. It interviews you
in rounds, looks facts up in the repos itself, then writes hub issues in
`.github/ISSUE_TEMPLATE/factory-requirement.md` (drafts in `factory/drafts/`) and creates
them only when you say so. `/grill-me` is the plain interview.

## Using the hub from GitHub Copilot (and other agents)

The skills and agents are written for Claude Code in `.claude/`. `factory/bin/copilot-sync`
mirrors them for Copilot: `.claude/skills/<name>/` → `.github/skills/<name>/` and
`.claude/agents/<name>.md` → `.github/agents/<name>.agent.md`. Edit the `.claude/` sources and
run `factory/bin/copilot-sync`; never edit the mirrors (`factory/bin/copilot-sync --check`
tells whether they're stale). When a skill or agent says:

- "call the Skill tool with `X`" → use the skill `X` (`/X`, or read `.github/skills/X/SKILL.md`);
- "dispatch a sub-agent", "an `Explore` sub-agent" → run a subagent if your tool can, otherwise
  do the lookup yourself;
- "spawn `<name>`", "the `<name>` agent" → the custom agent `<name>` (`.github/agents/<name>.agent.md`);
- `<hub>` → this folder.

`/factory run` needs Claude Code: the orchestrator relies on background agents, SendMessage and
Claude Code transcripts (for cost). From Copilot, use the scripts (`factory/bin/job queue`,
`job summary`, `job promote`, `job release ...`) and run single agents (intake, spec-writer,
reviewers) by hand. `/hub-init`, `/hub-onboard`, `/hub-dev-stack`, `/docs-sync`, `/grill-issue`
and `/grill-me` work in both.

## Software factory

Label a hub issue `factory` and run `/factory run`. Watch it with `factory/bin/serve`
(board and history on <http://localhost:8000/>). `README.md` explains the loop;
`.claude/skills/factory/SKILL.md` has the details.

## Setting up and maintaining the hub

```
/hub-init        goal (new project or existing system), sources, BRD, ADRs, specs, repos
/hub-onboard     check scripts that pass on every base branch; repos.json; AGENTS.md
/hub-dev-stack   dev/compose.yaml and dev/env/<key>.env
/docs-sync       re-read sources, update the documents that cite what changed
factory/bin/add-repo <url> | --create <owner/name> --yes    bring in or create a repo
```
